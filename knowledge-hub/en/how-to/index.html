How I use Claude

In fifteen months, the way I work with Claude has changed in nature. At first, a file of instructions pasted into a chat. Today, a system: a memory that knows me, a private brain, three ways of using Claude plus a browser, two agents, packaged procedures, tasks that run without me, and guardrails. Here's the setup as it actually runs — and where to start if you're just getting going.

By Hugo Lahutte · September 2, 2026 · First version: May 30, 2026 · ~14 min read

In 30 seconds

  • Context is everything, not the prompt. What makes Claude good in my setup is what it knows about me before I type the first line.
  • Three layers: memory (how to work with me — no more base instruction file, Claude remembers it), the Brain (what we know: entities, projects, decisions, method), and one CLAUDE.md per repository for the code rules.
  • Three doors plus a browser: Chat writes, Cowork executes office work, Code acts inside my projects in auto mode; Claude browses in Chrome or in its own browser for whatever has no connector. Two agents, skills, loops and routines for what runs without me.
  • The loop that makes it all grow: every error becomes a rule, every session becomes a capture. And one golden rule: the AI proposes, the human validates.

1. The principle: context is everything

When you're starting out, you think quality comes from the prompt — the right formula, the magic phrase. That's wrong, or rather it's 20% of the story. The other 80% is context: everything Claude knows before you write your first line. Who you are, what you do, how you like to be answered, what's already been decided, what's already broken.

The craft has had a name since 2025: context engineering. That's what my method is — organizing what Claude knows, in three layers that don't mix:

  • How to work with me → Claude's memory, and one CLAUDE.md per code repository (section 2).
  • What we know → the Brain, my private wiki (section 3).
  • What we know how to do → the skills, and the tools plugged in (section 7).

The first layer rarely changes (tone, rules, principles). The second changes all the time (projects, decisions, the state of ongoing work). Keeping them apart stops the rules from drowning in the facts, and the facts from hardening into rules.

Today's conversationThe request, the attached files, the tool results, what Claude reads in a browser. Ephemeral.
Memory + one CLAUDE.md per repository — “how to work with me”Tone, format, principles, preferences: remembered by Claude. Hard rules of a code repository: in a short, versioned file.
The Brain — “what we know”Entities, building blocks, projects, method, notes, sessions. Living, dated, private.
Skills and connectorsThe procedures loaded on demand, and the tools plugged in (Shopify, Drive, GitHub…).

2. What Claude knows about me: memory, plus one CLAUDE.md per repository

This is the most recent change, and the most counterintuitive for anyone who read the first version of this page: I no longer have a base instruction file. For fifteen months, a main CLAUDE.md (tone, principles, behavior rules) and its extensions by domain opened every conversation. They're no longer needed.

What replaced them: Claude's memory. Since August 25, 2026, it's a single memory shared between the chat and Cowork, on by default, and I can reread it topic by topic, correct it or erase it. The informal tone, “no preamble,” “one question at a time,” my job, my ongoing projects: Claude knows it when the conversation opens, with no file. Claude Code, for its part, keeps an automatic memory per project: it writes down on its own what it learns from a session — my corrections, my preferences, the traps it ran into — and rereads it the next time. A recurring correction no longer gets copied into a file: it's remembered.

What's still written by hand is a repository's CLAUDE.md: a code project's conventions, its commands, its forbidden actions, the traps that have already broken something. It's short, versioned with the code, and read by whoever works on the repository — human or agent. This site has one; Cobra has one per repository, with its hard deploy rules. It's no longer a personality file: it's the house rules.

Every brand also keeps its DNA file: history, positioning, what we say and what we don't. It lives in the Brain, loaded whenever Claude produces content about the brand. An hour of writing, and everything it produces goes up a level.

The sorting rule, which applies to everything: what's a matter of preference goes in memory; what commits a project goes in the Brain; what governs a repository goes in its CLAUDE.md.

3. The Brain: “what we know”

This is the real new thing of summer 2026. Until then, what I knew about my projects lived in Claude project documents, not shareable between tools, and in my head. Since August, all of it lives in a Brain: a private git repository of Markdown files with a small header (type, title, description, tags, date, confidentiality), organized in seven folders:

  • entities — the group's organizations (Cobra, Haute Fidélité, HiFi Lovers, HL Consulting…): what it is, where it lives online, my position, what runs on it;
  • building blocks — the systems under construction, with their living specifications and their dated decisions;
  • projects — anything with a beginning and an end;
  • method — how I work (prescriptive: a rule to follow);
  • notes — what I think (revisable: an opinion to cite, with its “what could take it down” section);
  • sessions — the raw log;
  • personal — always private.

The format is called OKF (Open Knowledge Format), an open specification published by Google Cloud in June 2026 that formalizes the “LLM wiki” popularized by Andrej Karpathy. Nothing to install: Markdown, links between files, an index at the root. My Claude instances read it through a plain GitHub connector, starting from the index and following the links. No vector database, no server — as long as navigation is enough. The day “find me what we said about order dedup” no longer surfaces the right document, that'll be the signal to build the index. Not before.

Memory and the Brain don't do the same job. Memory is implicit: Claude retains what it judges useful, and I review it after the fact. The Brain is chosen: explicit, reviewable, versioned, correctable by hand, read by all my tools. Whatever commits a decision or describes a project goes in the Brain; whatever is a matter of comfort stays in memory.

Two rules hold the Brain together:

  1. A stale brain is worse than an empty brain. A missing document triggers a search; a wrong document triggers a decision. Hence the capture ritual (section 9), which updates the reference pages and not just the log.
  2. We never invent the content of a shell (empty placeholder page). An empty doc that says it's empty is honest. A doc filled in by guesswork is a trap that goes off six months later, exactly when you trust it.

The Brain stays private. This Knowledge Hub is its curated version, rewritten to be read by humans and cited by AIs. Moving from one to the other is an editorial act, never a sync.

4. Chat, Cowork, Code — and the browser

Three doors into the same Claude, and a split that structures all my work:

ChatWrite, think
In my setup
Angle, text, tone, strategy. It has my voice, and my memory. We stop at Markdown: no HTML, no git.
Example
Writing this page, framing a spec, settling a positioning.
CoworkDelegate office work
In my setup
Files, spreadsheets, presentations, routines — no terminal. And its own browser, in the side panel, to finish an online procedure. On desktop, web and mobile.
Example
Preparing a deck, going through a file, filling in a supplier portal that has no connector.
CodeAct inside projects
In my setup
Reads and edits files, runs commands, deploys, updates the internal linking — in auto mode. In the terminal, on the web or from my phone.
Example
An Odoo module, this page live a minute after the push, an internal app.

The boundary rule is simple and I stick to it: Chat writes, Code executes. A Chat session produces a validated Markdown; Code turns it into a deliverable (HTML page, JSON-LD, sitemap, llms.txt, commit, push). The two halves have different success criteria — the accuracy of the argument on one side, conformance to the template on the other. Mixing them in one session means losing both.

And the browser. Since August 26, 2026, Claude can browse: read a page, click, fill in a form, move from one tab to another. Two ways: the Claude in Chrome extension, in my own browser (all paid plans, desktop Chrome), and Cowork's built-in browser, separate from my tabs and my passwords — nothing is shared, except the credentials I import site by site. It's the door for everything that has no connector: a supplier portal, a back office without an API, an administrative procedure, checking a page online after publishing. Same rule as for connectors: Claude reads and prepares; the final click — pay, send, validate — stays mine.

5. Auto mode: you no longer validate each command, you validate the result

Until the summer, Claude Code asked for permission before every command, every file it changed. Since August 14, 2026, auto mode is the default: Claude chains actions without asking, and a classifier — a second model — reviews each action before it goes out. It blocks whatever goes beyond the request, whatever touches infrastructure it doesn't recognize as mine, and whatever seems dictated by hostile content Claude has read (a prompt injection). My prohibition rules take precedence over it: what I've forbidden stays forbidden, whatever the classifier thinks.

A September 2026 benchmark, measured by Anthropic on a thousand testers: humans intercepted 13.6% of dangerous commands when reviewing every request, versus 89% for auto mode — and human vigilance dropped to 5% after fifty approvals. In other words: clicking “yes” fifty times in a row protected nothing. What that changes in my practice:

  • I no longer validate the commands, I validate the result: the diff, the health-check script that passes, the page live online. It's the “goal-driven” principle applied to execution.
  • The forbidden actions are written down, not repeated: never a force-push to the production branch, never a secret in a file, never a whole branch deployed. A prohibition rule in the repository beats an instruction I keep repeating.
  • Business validation doesn't move: auto mode covers a project's commands, not the writes into my tools. Changing a price, sending an email, publishing: still a preview and a button (section 10). Anthropic says the same thing: human review for anything that touches production.

6. Two agents, two accounts

I run two Claude instances, deliberately kept apart:

  • Claude · HL — my personal account: steering, strategy, editorial, method, this site, the group's building blocks. Its memory, its connectors, its projects.
  • Claude · Cobra — the company account: Odoo and Shopify development, purely technical. It knows the codebase by heart, reads the CLAUDE.md files of the Cobra repositories, and never talks about my personal projects.

Both write in the same journal (the Claude · HL and Claude · Cobra badges on each entry) and read the same Brain — but the Cobra Claude only writes to the Cobra pages, the sessions and the technical building blocks. Not a technical permission: a governance rule, so as not to mix two perimeters in a base read from both sides. And when a project is run elsewhere — Growth, built with ChatGPT and Codex — it carries its own badge.

7. Skills and connectors: the procedures and the arms

Two building blocks have taken up a lot of room this year.

Skills. A skill is a procedure packaged in a folder (a SKILL.md file, sometimes scripts) that Claude loads when the situation calls for it. In my setup, three do most of the work:

  • kh-post-brief — at the end of a session, with any AI, produce the brief for a journal entry: title, vertical, tags from the whitelist, sections, sanitization guardrails. I paste the brief into Claude Code, which publishes the FR + EN entry and all the internal linking.
  • brain — read, search and update the Brain, with a strict write gate: never a write without an explicit instruction.
  • wiki-capture — the end-of-session ritual (section 9).

A skill's strength: it's portable. The text of kh-post-brief works pasted into ChatGPT or Gemini. It's written method, not magic. And Cowork can build one by watching me work: I record my screen while narrating, and it turns that into a reusable skill.

Connectors. Claude plugged into my tools through the MCP standard: Shopify (both stores), Google Drive, Gmail, GitHub, Qonto, the host of my apps, Odoo through code. Result: it works on my real tools, not on a demo — and it can now send an email or move a file, under validation. Whatever has no connector goes through the browser (section 4). One non-negotiable rule: the assistant never has more rights than the person talking to it.

8. Loops and routines: what runs without me

A growing share of my work with Claude no longer happens in a conversation: it runs. Three forms, depending on how long the need lasts:

  • The loop — in Claude Code, a command re-runs a prompt at a regular interval during my session: monitoring a deploy this afternoon, checking every ten minutes that the key pages respond. It lives with the session and expires on its own. In auto mode, it runs without asking me anything.
  • The routine — scheduled (every morning, every Monday) and executed in the cloud on Claude's side, without my machine: this site's weekly consistency check, a seven-day watch on my audience analytics, read-only.
  • The home-made scheduled task — cron, GitHub Actions, a small server, for what has to run every day, forever, with its secrets on the server side: my two daily watches, the site's regeneration at every publication.

The rule that applies to all three: a recurring task reads and alerts, it doesn't write on its own into a production tool. And each one has its frame before being launched: goal, budget cap, bounded frequency, stop criterion.

9. The loop: every error becomes a rule, every session a capture

The guiding principle is still Compound Engineering: when Claude trips over a recurring point, I don't grumble, the lesson is retained — in memory, where Claude Code often writes it down itself, or in the repository's CLAUDE.md when it's a code rule. An Odoo production release that broke several things became a hard rule of the Cobra repository; an agent burning through its budget in a loop became a standard guardrail.

Since August, the loop has a second level. At the end of a session, the capture skill does four things, in this order: reread the session and identify the entity and the topic; write the sessions/ entry in the OKF format; propose targeted changes to the reference pages affected (building blocks, entities); run the confidentiality filter and propose the commit. The third point is the one you're tempted to skip — so it's the one at the top of the procedure. Without it, the log grows while the pages go stale in silence.

The trigger isn't automatic, and that's deliberate: no mechanism fires reliably on “the conversation is getting long” across every client. Instead, a rule Claude holds in memory: when the conversation gets long, it offers to wrap up with a handoff brief — and to capture into the Brain. It works everywhere, including on mobile, with no infrastructure.

Do→ Spot the error or the lesson→ Rule retained (memory, repository CLAUDE.md)+ Capture into the Brain→ Next session, higher up every session

10. The guardrails: the AI proposes, the human validates

The more Claude acts, the more the framework matters. The rules I apply everywhere, from the smallest script to my internal systems:

  • An agent has four things before it's launched: an explicit goal (“we'll know it's good when…”), a budget cap, a bounded frequency, a measurable success criterion.
  • Automatic reads, validated writes. Reading, refreshing, proposing: automatic. Changing a price, a stock level, a campaign, an email, a publication: human validation. The standard flow: request → analysis → preview of the change → validation → execution → log → measurement. Claude Code's auto mode changes nothing about this rule: it covers a project's commands, not my tools.
  • Three regimes depending on the nature of the action: mechanical = automatic; factual reply = generated then validated with one button; judgment = human draft, always.
  • Check before coding. My Odoo change-request pipeline has the AI review every request in two passes: it asks structured questions, the server checks them against the real database in read-only mode, the AI concludes. It has already requalified a development request into ten minutes of configuration.
  • The browser has the same rules as the connectors: Claude reads and fills in; it doesn't pay, doesn't send, doesn't validate on my behalf. No credentials stored beyond what's necessary, and a booby-trapped web page can't make it do what I didn't ask for — that's exactly what the auto mode classifier and the limited rights are there to block.
  • No secrets in the code or in the Brain, surgical deploys (never a whole branch, always the exact commit), no cron that publishes on its own.

11. Where to start

Four months ago, I advised writing an instruction file before anything else. Not anymore. My recommendation, in order:

  1. Let memory do the work. Open Claude, check that memory is turned on, and spend one conversation telling it how you work with the prompt below: tone, format, job, what you don't want. Then reread what it retained in the settings, and correct it. One hour, and you stop re-explaining yourself — with no file.
  2. Write the DNA file for your company or brand. That's where communications and content go up a level.
  3. Open a minimal Brain: a folder with an index.md, one page per organization (“what it is, where it is, my position, what runs on it”) and one method page. Markdown, a private repository, a connector. The rest fills in session after session — and never invent a page you don't know how to fill in.
  4. Move to Cowork or Code when you want Claude to do, not just answer — and to its browser for whatever has no connector. Set the four guardrails before the first agent. A CLAUDE.md only if you have a code repository: its rules, its forbidden actions, in ten lines.
  5. Run a first chore without you: a loop to monitor something this afternoon, then a weekly routine, read-only.

The prompt to copy and paste to set up your starting context:

Prompt — set up your starting context (memory, DNA, Brain)I want you to know me before we work together, and to set up my context system: what you should remember about me, a DNA file for my organization, and a minimal Brain. Method: ask me ONE question at a time. We move forward section by section. Don't guess anything: if I don't answer, the section stays empty. 1. What you should remember about me (to keep in memory, with no file): - My tone and preferred format (formal or informal? prose or lists? how long should answers be?) - My professional context: what I do, my company, my industry, my role - My rules: web search on anything that may have changed, honesty, no flattery, “I don't know” rather than making things up, push back if my idea is bad - What I DON'T want (preambles, end-of-answer summaries, frameworks I didn't ask for, over-complication) - When the conversation gets long: offer to wrap up with a handoff brief At the end, summarize in ten lines what you've retained, so I can check your memory. 2. A [NameOfMyOrganization].md file that describes its DNA: - History and context - What we do, for whom, why - Positioning and values - Brand tone: what we say, what we don't say 3. A minimal Brain: an index.md and, for each important organization in my professional life, a Markdown page with a header (type, title, description, tags, timestamp, confidentialite) that answers four questions — what it is, where it lives online, what my position is, what systems run on it. If you don't know how to fill in a section, leave it empty and ask me: don't make anything up. 4. Only if I have a code repository: a ten-line CLAUDE.md for that repository — conventions, commands, forbidden actions. No personality in it: you already know me. When we've covered everything, generate each complete file in Markdown, separately.

That's all you need to get started. The rest builds itself through use: every friction becomes a remembered rule, every session becomes a capture, and your system gets better on its own.

12. What's changed since May 2026

For those who read the first version of this page — or who want to gauge how fast the ways of working are moving:

  • No more base instruction file (September): memory, unified between the chat and Cowork since August 25, and Claude Code's automatic memory, carry “how to work with me.” All that's left is one CLAUDE.md per code repository, short, for its rules.
  • Auto mode is the default (August 14): you no longer validate each command, you validate the result; a classifier blocks escalation and injections; the forbidden actions are written in the repository.
  • Claude browses (August 26): the Claude in Chrome extension in my browser, or Cowork's built-in browser, for everything that has no connector — with the same guardrails.
  • Loops and routines for what runs without me: monitor this afternoon, check every week, read-only.
  • The Brain exists (August 2026): knowledge has moved out of project documents to become a private wiki, readable by all my tools.
  • Cowork has become a real third door: desktop, web, mobile, browser, memory unified with the chat, scheduled routines, skills learned by recording the screen.
  • Skills have replaced reusable prompts. A procedure lives in a folder, not in a notepad.
  • Connectors act, not just read: sending an email, managing a file — under validation.
  • The Claude 5 family (Sonnet 5 in June, Opus 5 in July, Fable 5.1 on September 1) has changed the math: the right model is still the cheapest one that does the job, but “the job” has become much longer and more autonomous.
  • Guardrails have become systems, not instructions: validation before writing, log, measurement after action.
