Writing a good CLAUDE.md (when you still need one)

In 2026, you no longer need a base CLAUDE.md: Claude's memory retains your tone, your rules, and your preferences. There's one case left where the file matters, and it matters a lot: the repository — a site, an app, a code project. What goes in it, how it grows, where it lives, and what it isn't.

In 30 seconds

  • A CLAUDE.md is a context file that Claude reads at startup in a repository: conventions, commands, prohibitions, pitfalls turned into rules.
  • What it no longer is in 2026: the personality file you pasted everywhere. Tone, preferences, and behavior rules live in Claude's memory (unified across chat and Cowork, on by default); Claude Code notes your corrections on its own in a per-project memory.
  • What's left: a repository's house rules, read by whoever works on it, human or agent — especially in auto mode, where a written prohibition beats a repeated instruction. Short, versioned, re-read on a fixed date. Facts go elsewhere (the Brain), and so do procedures (skills).

1. What it no longer is, and what's left

In May, this guide opened on “the best investment”: without a CLAUDE.md, you re-brief Claude in every conversation; with one, it's framed once and for all. That was true. It's no longer quite true, and that's good news: you no longer need a base file. Since August 25, 2026, Claude's memory is a single one across chat and Cowork, and on by default: the casual register, “get to the point,” your line of work, your ongoing projects — it retains them, and you can re-read, correct, or erase what it has retained, topic by topic. Claude Code, for its part, keeps an automatic memory per project: it notes on its own what it learns from a session — your corrections, your preferences — and re-reads it the next time.

What's left, and has never been more useful: a repository's CLAUDE.md. A site, an app, a code project have conventions, commands, prohibitions that don't depend on you but on the project — and that have to be read by whoever works on it, human or agent, on any machine. Now that Claude Code chains commands without asking (auto mode), a prohibition written in the repository beats any repeated instruction: “never force-push to the production branch” gets read there before the first command, and my prohibition rules come before the classifier. The rest of this guide is about that file.

2. What goes in it

Four families of things:

  • Tone & format: casual or formal, prose or lists, short or detailed.
  • Your conventions: your line of work, your tools, your in-house vocabulary.
  • What you DON'T want: empty jargon, unrequested 14-step plans, flattery…
  • Your pitfalls: the mistakes already hit, turned into rules. That's the part with the most value.

And two operating rules I added this year, because no tool can do them in place of the instruction: context management (“when the conversation gets long, offer to close with a handoff brief — and to capture into the Brain”) and the extraction rule (“when I state a principle that would hold in another project, offer in one line to keep it as a note; a single offer per conversation”).

3. Best practices

  • Short beats exhaustive. A file nobody reads is useless — and it's re-read with every answer, so it costs with every answer.
  • Concrete beats abstract. “Give me the commands ready to paste” rather than “be helpful.”
  • One rule = one real mistake. Don't add speculative “just in case” rules.
  • Split by context. Rather than one big slab, a shared foundation + extensions (one for strategy, one for tech, one per project).
  • No facts that change. A module count, a server name, the status of a project: it goes stale, and a wrong rule is worse than a missing one. Those facts live in the Brain, dated.

4. How to grow it

When Claude screws up on something recurring, you don't grumble: you add the rule. The file improves with use. It's exactly the principle of Compound Engineering applied to your context.

But you also have to know how to re-read it. In June, I reopened the context files of my Cobra project, written a month earlier: the hosting had changed, so had the deploy workflow, the module count was wrong. Claude was starting every session with a mistaken mental model of the infrastructure. Since then, a re-read on a fixed date, and a cleanup command in Claude Code that spots duplicates and unused files.

5. Where it lives, and how to split it

At first, my files lived in a chat's “Project Instructions,” then in a docs/ folder with a shared foundation and extensions per domain (CLAUDE-strat.md, CLAUDE-dev.md, CLAUDE-dev-cobra.md). The foundation and the strategy extension are gone — memory carries them now. What's left lives at the root of each repository, next to the code, versioned: Claude Code automatically reads a project's CLAUDE.md when it opens it.

  • CLAUDE.md at the root — the repository's rules: conventions, commands, prohibitions, pitfalls, publishing procedure. Short.
  • One file per sub-project only when a repository holds several (CLAUDE-dev-cobra.md for the hard Odoo deploy rules, next to a generic technical foundation).
  • This site is the public example: its CLAUDE.md describes the stack, the rules for every page, the allowed tags, the procedure for adding a journal entry — nothing about my tone, which Claude has in memory.

A versioned file has a history: you know who added which rule, when, and after which incident. And a Claude Code command (/checkup, since July) tidies up what's lying around: duplicate files, unused skills and connectors.

6. What it isn't: memory, Brain, skill, hook

CLAUDE.md long served as a catch-all. In 2026, four things moved out of it, and it's all the better for it:

  • Personality and preferences → memory. Tone, format, “one question at a time,” what you don't want: Claude retains it on its own, everywhere. CLAUDE.md says how we work on this repository, not how to talk to you.
  • Facts → the Brain. What we know (entities, projects, decisions, project status) changes all the time; it belongs in dated pages, loaded on demand. CLAUDE.md says how to work, not what.
  • Procedures → skills. A twenty-step procedure has no business in a file re-read with every answer; it lives in a folder, loaded when the request matches.
  • Reflexes that must always run → hooks. “Never merge the whole branch” is a rule you read; a hook that blocks the command is a rule you can't forget.

What stays in CLAUDE.md is what has to be there every time this repository is opened: conventions, commands, prohibitions, pitfalls. It's short. That's on purpose.
