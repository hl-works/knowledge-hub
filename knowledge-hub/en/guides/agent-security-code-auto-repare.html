Case study · Enhanced security

An agent that watches
the agents that code

Finding alerts is easy. Building a system that knows which ones matter, keeps access under control, and prepares a verifiable fix is far more interesting.

By Hugo Lahutte·September 4, 2026·Updated September 7·~14 min read

In 30 seconds

Agent Security monitors multiple GitHub repos with open source tools, keeps a memory of issues, and prepares fixes in a sandboxed area. The scanner can't write. The fixer only gets targeted access. Multiple models can disagree with each other, but the scanners and tests have the final word.

1. The full circuit

A single agent that can read, modify, and publish would be convenient — and dangerous. The system is split into two trust planes. Agent Security observes. Agent Security Fix repairs. Neither one decides alone what goes to production.

Simple version: the guard can look anywhere, but doesn't have the keys. The repair tech gets a temporary key for one door only. They propose their fix, several checks verify it, then the production gate opens — or stays closed.

2. The gateway: precise access, never a master key

Each GitHub organization has its own installation. At scan time, the gateway creates a short-lived token, scoped to visible repositories and the necessary permissions. An unknown owner, an out-of-scope repo, or an inconsistent response blocks the operation.

3. What runs automatically

Depth scales with risk. There's no need to re-run the most expensive check every night; but there's also no reason to wait three months to discover a secret committed yesterday.

On every sensitive changeTargeted check

Authentication, permissions, secrets, payments, database, CI, or deployment.

Every weekLight audit

Secrets, dependencies, and newly known vulnerabilities.

Every monthDeep audit

Full static analysis, containers, IaC, and configuration.

Every quarterAdversarial review

Threat landscape, supply chain, architecture, and exposed surfaces.

Tools also update themselves via PR. A new version is analyzed, tested, and stays traceable. The goal isn't "always the latest," but "recent without blindly accepting a supply chain compromise."

4. In HL‑OS: see, understand, trigger

HL‑OS is the human cockpit of the system. It doesn't replace the scanners — it turns their evidence into an actionable view, with an overall score, repos, risks, available fixes, and history.

1Collect

Read private reports without displaying the value of a secret.

2Decide

Separate confirmed finding, false positive, tool failure, and available fix.

3Trigger

Launch a plan and track agents, PRs, tests, and re-verification.

4Trace

Retain models, commits, rejections, results, and production releases.

5. A fix isn't a promise — it's proof

The fixer can't just reply "it's done." The original finding is tied to a specific commit. After the change, the same scanner must be replayed, then the project's own tests.

Fail closed: if a tool crashes, a report is unreadable, or an access fails, the repo is never declared clean. Absence of proof remains a state to be checked.

6. Claude proposes. ChatGPT verifies. Kimi tries to break it.

The names below are an example — models remain configurable via OpenRouter. The key idea is to use different model families with separate roles, so no agent simply validates its own intuition.

CURRENT STATE

Multi-model cross-analysis is available as advisory input on manually triggered audits. It doesn't yet automatically drive every fix all the way to production.

TARGET

Every eligible fix must go through this chain. An objection loops back to the fixer; agreement only opens the door to testing.

Why not just run Claude → ChatGPT → Kimi in free conversation? Because an early error would contaminate the rest. The controller gives each model the original evidence and collects a structured verdict. They can see the diff, but must reason through it independently.

Memory and traceability

Each finding gets a stable fingerprint without secrets, its first-seen date, its last-seen date, and its status: new, recurring, resolved, or reopened. Decisions and exceptions are kept separately in a versioned registry; temporarily accepting a risk doesn't technically suppress the alert.

AI request confidentiality

Scheduled audits send nothing to models by default. When an OpenRouter analysis is explicitly enabled, only the necessary metadata is transmitted — never the full repo, the value of a secret, or the raw match. Responses are requested as strict JSON with the specific model, its role, its confidence, and the cited findings.

The guiding principle

Maximizing automation doesn't mean removing controls. It means replacing unnecessary clicks with evidence, independent agents, and an explicit policy — while keeping a human stop wherever a mistake would be hard to undo.
